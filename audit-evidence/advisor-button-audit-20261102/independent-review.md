# Independent state-lifecycle review

Reviewed the current local `advisor.js`, `advisor_flow.py`, and `natural_flow.py` changes against the packet's retained before copies, with additional direct calls to production controller methods. No browser or external AI/model calls were used. One typed-retraction reproduction used the existing deterministic in-process Responses transport; it did not access the network or provider credits.

Confirmed findings sent to the owning implementers:

1. **Retired names could return without a new report.** After entering a doctor/medicine, selecting No doctors/No prescriptions, then reporting a new item, the old name reappeared in the newly active guide field. The new fix archives the retired aggregate in bounded report history and starts an active collection from only the newly supplied item, with a new item ID. Direct capture/apply rechecks passed for both doctors and medicines: only the new name is active, the new detail report is current, and the old collection remains in history.
2. **A pending multi-field clarification could not complete one field at a time.** An RC16 target containing `start` and `priorMedigap` remained pending after two successive exact field submissions. The new fix subtracts only explicitly answered keys for the same question and item. A direct controller recheck passed: the first finite submission leaves only `start`; the second clears the queue.
3. **Reading an explanation invalidated an otherwise unchanged clarification queue.** A concept action incremented the record revision without updating the pending queue's revision, so the next eligibility computation discarded both pending medicine targets. The new utility fix keeps queue revisions aligned across harmless presentation actions. A direct concept→eligible recheck retained both exact pending item targets.
4. **Typed No prescriptions/No doctors needed the same pending-target cancellation as their finite buttons.** A scripted accepted T07 `no` report still left old medicine-strength targets pending. The backend implementer was notified to share the cancellation logic across typed and finite accepted reports while retaining unrelated pending targets.
5. **A lost DELETE response is different from a rejected DELETE.** If server-side deletion succeeds but its response is lost, the old owner/CSRF/continuation must not remain the presumed usable authority. The utility implementer was notified to reconcile this uncertainty without automatically repeating deletion or saving an old snapshot.

The typed-retraction recheck now clears the medicine clarification queue and advances to another relevant question while keeping the explicit No prescriptions report. Final uncertain-deletion/session helpers were independently read: network uncertainty pauses saving, clears possibly revoked tokens and pending saves, and checks actual saved versions before a free owner refresh; an HTTP rejection preserves the current visit's authority. No stale snapshot is automatically saved or deletion automatically repeated.

The parent packet owns the final suite and activation results. This note records the independent findings and targeted rechecks, rather than treating passing tests as consumer approval or claiming that earlier unrelated incidents were resolved.
