## Assessment

Daylight has progressed well beyond a document collection and UI prototype. It has a substantial versioned Medicare research corpus, deliberate evidence governance, a full local fifteen-layer PostgreSQL population, source-preserving adapters, and the beginnings of a useful source-backed identity/research loop. It does not yet have an accepted consumer advice engine, a demonstrated cloud-operating environment, or a proven continuing data-maintenance operation. The largest remaining work is complete meaning and exact scope, permission and release machinery, personal coverage/cost models, current-source verification, and clean operational recovery. Moving the files to a cloud does not close these gaps.

The 15 business capabilities in the owner's request are different from the 15 Medicare data layers. Neither should be described as 15 finished modules. There is no valid overall percentage obtained by dividing accepted entries by source rows or semantic obligations.

The primary narrative is consistent with [PRINCIPLES.md](../../../PRINCIPLES.md): a self-service AI Medicare advisor that teaches, investigates and supports an informed decision while the person retains control. The data strategy supports that narrative when it yields fewer consequential questions, understandable evidence, useful work and honest uncertainty. Corpus size and test counts are infrastructure measures, not the customer proposition.

## Organize and migrate without breaking evidence

1. Keep code, deployable configuration, migrations, synthetic fixtures, concise current documentation, and small exact manifests/receipts in the collaboration repository after secret/source-use review. Keep raw carrier/CMS payloads, generated large source stores, PostgreSQL cluster files, dumps, customer stores and secrets out of ordinary source history. Retain immutable originals; generate the GitHub export as a separate controlled projection rather than deleting files from this working research tree.
2. Store immutable original evidence/receipt bundles in private content-addressed object storage. Every object needs digest, length, original locator, layer/revision/role, clock, access/use state and restore mapping. Preserve original path strings in evidence even if the cloud object key changes. Add a relocation manifest/lookup overlay; do not rewrite frozen paths/hashes or rename sealed evidence in place to make the tree attractive.
3. Put operational relational data into a managed PostgreSQL target that passes this actual schema/role/migration/extension/version rehearsal. Provider choice can be Supabase or AWS only after compatibility, restore, permissions, scale and cost are verified. Existing infrastructure is PostgreSQL-centric, so do not re-model all evidence merely because the chosen host offers a separate API. Avoid exposing research tables directly to client browsers.
4. Keep customer profiles, consent, guest authority and permissions in a separately controlled data boundary from source research. Existing guest stores are excluded from the load and need their own explicit migration/cross-device/auth/retention design. Move no real guest store as part of an evidence backup task.
5. Preserve source STOP states and exact purpose-based rights in the target. An internal credential, public download, bucket upload or queryable row is not permission for consumer redisplay, model context or recommendations. Exact accepted references need original authority replay, freshness/revocation and version composition, not blanket accepted=true.
6. Rehearse on an isolated target: role creation/migrations, complete restore, external-object restore, hash/row/condition/key parity, expected holds, permissions, concurrency and query limits, failure/retry/rollback. Record actual target/image/versions and source composition. Only after this is proven cut a reviewable collaboration/deployment candidate.
7. Use separate immutable release-selection manifests and additive current navigation. Resolve stale readmes via an external current-state index, not mutation of sealed history. Delegate work by layer, source family, semantic ownership and code boundary so multiple contributors cannot each claim the same IDs or accept their own data work.

## Collier MVP sequence

The education and reported-profile product can be evaluated now within existing gates. The company narrative includes helping choose coverage; a fully useful choice service still depends on real coverage checks and accepted comparison behavior. An education-only pilot should be labeled as that pilot, never called completion of the full advisor or the existing L03 obligations.

1. Define the first supported consumer task and benefit year. Most selected evidence is 2026 while retained samples are 2027. A historical 2026 research demonstration is viable; present or upcoming consumer selection needs every material layer for the explicitly chosen year. The 2027 L02 regression (59 observed Collier identities) alone does not provide 2027 benefits/drugs/networks/pricing. Keep this a scope decision rather than silently substituting years.
2. Finish the current whole-offering source-first L03 pilot and exact accounting/review; use its failure taxonomy to estimate remaining full-scope work. Finish internal scope/unit/condition reconciliation concurrently with genuine permitted-source requests. Do not reinterpret a cloud deadline as an evidence exemption.
3. Establish the accepted Collier available-market and coverage-path scope, including Original Medicare + Medigap + PDP, MA, current coverage/deferral and other relevant paths. Close exact address/status/restriction and source-use gaps before presenting 72 observed MA records as available choices.
4. Build one reviewed consequential research flow end to end: confirmed person facts → exact medicine/provider/outlet candidates → accepted plan/year/site/condition check → explicit outcome and uncertainties → correction/replay → stable summary. An identity candidate selection is the starting point of verification, not its endpoint.
5. Define and independently validate the coverage-path/comparison model, personal cost assumptions and material policy rights. Show the same fact/evidence/priority result when commercial inputs change. Keep verified evidence separate from self-reported facts and unknowns.
6. Pass cloud restore/permissions/runtime and actual merged-app compatibility gates; preserve source and guest boundaries. Choose named operational owners for refresh, review, incident handling and release decisions before multi-person live work.
7. Observe a small first-time-enrollee cohort with declared success criteria: correct understanding, retained control/corrections, useful completed tasks, unresolved-case quality, staff effort and neutral outcomes. Track maintenance/reviewer time alongside AI/hosting cost; the emerging manual semantic-review cost matters at least as much as raw infrastructure cost.
