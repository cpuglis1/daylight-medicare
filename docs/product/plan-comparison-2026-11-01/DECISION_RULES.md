# Proposed comparison and next-question rules

November 1, 2026 · `daylight-comparison-rules-design-r1` · Structural rules proposed for review; no executable Medicare policy or live matcher.

The 41-question contract supplies meanings and dependencies. The profile supplies scoped reports. The evidence database supplies immutable observations and their limitations. This proposed rule layer joins those three without treating an answer, a source observation or a passed technical check as permission to make a personal finding.

## Evaluation procedure

1. Bind the explicit task, beneficiary, relevant profile revisions and comparison scope. Resolve consequential ambiguity before dependent use; preserve unrelated clear reports.
2. Derive the required inputs for each requested finding from existing branch meanings. Reuse supplied reports and aliases. Optional preferences never gate factual availability.
3. Establish the current arrangement and coverage-path context. Prepare the candidate-universe ledger with exact market/year/role and visible unsupported/restricted options.
4. Resolve item identities and attach evidence at its actual grain. Evaluate the complete conditions under the exact reviewed method. Produce a result for each relevant dimension, retaining unresolved conditions and source disagreements.
5. Check output authority independently for each finding and action. A sufficient input report can still have a held finding. Published display, comparison, ranking, recommendation, quote and enrollment need separate exact-purpose authority.
6. Produce supported tradeoffs, neutral ordering, current/keep/defer outcomes and a dependency trace. Pick at most one consequential user question. Put external work in separate work items.
7. Recheck bound revisions/revocations before returning. Discard stale derived conclusions, preserve reports and re-evaluate affected work against a new consistent snapshot.

Every applied rule records its ID/version, input refs and revisions, required evidence/policy refs, evaluated predicates, result, reason codes and invalidation keys. Source/method/purpose scope is part of the rule contract. No rule body may fill an unknown with an assumed default.

## Granular matching algorithm

Define a matrix over **comparison unit × requested dimension × care item/scenario × period**. A provider row uses a specific office; a medicine row uses a specific product and fill; travel can have several places; the current arrangement has the same rows. Each cell retains complete conditions and orthogonal status axes from the response contract.

For an explicit constraint, partition candidates as `known_meets`, `known_conflicts` and `unresolved` using released findings. An unknown must-have cannot be certified, and cannot become a known conflict. These groups are an inspectable view, not a silent exclusion. Only an explicit supported filter may hide known conflicts, with counts/reasons and a clear way to restore them. Unknown options remain discoverable. Scope exclusions similarly need exact reasons and a separate ledger; catalog availability never establishes personal enrollment eligibility.

With no expressed priorities, show the common dimensions without invented weights. With an unordered priority set, emphasize those dimensions and explain the supported differences. A precise stated priority order could later support a reviewed lexicographic method, but this first design does not activate automatic personal ordering. No click-order weights, opaque embedding similarity or LLM-assigned fit score.

For a supported numeric row, compute a direction only when value/basis/period and scope are comparable. A difference in plan premium may be described as such; it is not annual savings or a path total. For categorical rows, compare the same exact condition-aware assertion. Evidence that a requirement is supported is distinct from a resolved adverse result, a source dispute and unknown evidence.

An optional pairwise relation may say “no worse on this named comparable subset, and better on this named row.” It must list excluded/material unresolved dimensions and cannot imply overall dominance or recommendation. Establishing **overall** dominance would require all material constraints/dimensions, complete common scope and accepted methods; otherwise the result is `tradeoff_or_unresolved`. Never use data completeness itself as a suitability advantage. Ties remain ties; a deterministic source-order tie-break is procedural only.

For complicated cases, preserve several explicit scenarios rather than inventing an average beneficiary. For example, a defined fill scenario and a defined routine-away-care scenario can each reveal which facts or conditions could change the comparison. No probability, annual utilization, budget inclusions or risk tolerance is inferred. The person can revise a priority or constraint naturally; the dependency graph recomputes only its affected findings/relations.

## Selecting a question without another questionnaire

Build eligible targets from the 41-ID map and the requested findings. A target must identify a missing meaning, person/item, affected finding and why an answer can change the next supported decision or materially scope research. Known facts and child aliases are deduplicated by canonical field/item/revision.

Use the latest owner guidance over old inventory dependency/wording metadata. The map preserves original `source_dependencies` for audit; these do not themselves become mandatory consumer gates. RC24 can support a narrower rule-specific check without full RC23 pricing; optional RC25 earns no automatic assistance/year interview. RC13 includes relevant own-benefit consequences even without a covered relative. Exact accepted finding rules supply the actual minimum dependencies, with any historical-policy conflict explicitly reviewed before activation.

Use a deterministic priority tuple rather than an invented expected-information score:

1. Consequential ambiguity/correction or an explicit immediate interruption needing a supported response.
2. A missing mandatory dependency for the current requested finding.
3. A report whose plausible answers change a material comparison dimension or the exact external research target.
4. A lower-burden eligible target within the active concern; preserve conversational continuity among ties.

The model may choose wording and select among service-approved equally eligible moves. It cannot add a question meaning, bypass a mandatory dependency or infer a required answer. Optional T02 is not insurance-input readiness. T09/T10/RC25 are optional tradeoff context; do not make the person choose priorities to see factual options.

For the proposed implementation, record a service-generated key for each eligible target: `(blocking_class, concern_distance, burden_class, inventory_index, stable_item_id, target_path)`. `blocking_class` follows the four priorities above. `concern_distance` is zero for the explicit active concern, one for its immediate finding dependency and two for another relevant concern. Proposed burden classes are finite direct answer, single typed value, grouped related known values, and information requiring outside retrieval, in that order; these are transparent scheduling proxies, not measured effort or a claim that forms always feel easier. Do not require outside document retrieval when useful help/defer is appropriate. Evaluate actual user burden before release.

The model may select within targets tied on the first three key components, and its committed choice/method version becomes part of the visit trace. The deterministic fallback takes the lowest complete key, using the immutable 41-ID inventory order then stable item ID/path for ties. Replay returns the committed selection rather than sampling a new one; an updated profile/task re-evaluates eligibility. Invalid or failed composition leaves the canonical fallback available without a paid repair call. This specifies next-move mechanics; actual branch classifiers and dimension-specific comparison/condition truth tables still require implementation and review.

If the only blocker is a source, policy or release hold, return that work item. Do not invent customer questions to appear productive. A report can still be requested when it would materially identify the external research task, with that limited purpose stated. Unknown/defer/decline suppresses a repeated target for the same task/revision; reopen only after the person requests it or a material dependency change creates a new reason. Optional inspection is not mandatory confirmation of each reply.

The three child aliases do not add obligations. RC11.C1 fills only `coverageEnd`, leaving `jobEnd` independent. RC16.C1 fills the relevant actual Advantage episode start, with first-entry/history conditions kept distinct; desired future start cannot substitute. RC16.C2 fills prior Medigap/transition-link meaning in the relevant scope, without establishing lifetime absence, reinstatement or the same price. RC29 is the external/source guard; RC30 is the future named-action guard. Neither is an intake question.

## Dependency examples

| Change | Invalidate/reassess | Preserve |
|---|---|---|
| One medicine's strength/form | Its identity/formulary/fill findings, dependent totals and tradeoffs; price requests bound to the old revision | Other medicines, providers and unrelated reports |
| County/year/beneficiary | Affected candidate universe and all claims bound to old scope; old result/action tokens | Reports kept with their original subject/scope, not reassigned to a new beneficiary |
| Eligibility basis | Basis-dependent timing/coordination and RC10 threshold interpretation | The historical answer and its original question meaning; it cannot answer a different threshold |
| Requested start becomes soonest | Old exact-month dependent work | The soonest preference without an invented date; unrelated actual coverage dates |
| Priorities or explicit reason | Emphasis, constraints/tradeoff relations, next research priority and explanation bindings | Independent evidence values and unrelated factual reports |
| Source edition/revocation/dispute | All dependent released findings, comparisons and action tokens | Prior immutable evidence/history, clearly historical results and unaffected findings |

## Connecting this to PostgreSQL

Propose a small private service behind the existing session-owning backend. The browser sends a task and server-issued case/revision binding; it does not receive a database credential or authoritative completeness flag. The backend reads only permitted profile values, and the comparison service uses a restricted accepted-evidence reader. Do not forward all customer data to the research service.

Serving structures would be versioned and separate from immutable `dl_evidence` research: an exact-scope candidate index, coverage-component/product identities, condition-preserving accepted facts, care-item source bindings, and rule/release manifests. Index actual year/geography/category/offering/source-identity query paths. Preserve the [validated Collier research bridge](../../data/infrastructure-execution-2026-10-30-local-full-db/build-r3/COLLIER_BRIDGE_INDEPENDENT_QA.json): native `raw.id` and projected `fields.id` agree for all 72 offerings, with national/r9 identities reconciled. The remaining work is a normalized accepted serving identity/release binding, including the presently null typed offering join; it is not missing source identity or a reason to redo validated acquisition. Do not substitute name joins or force Medigap into the CMS offering key. Validate a complete new serving build and exact authority before selecting it; pin each response to that build and retain rollback/revocation behavior.

Batch a candidate set's dimension lookups and retrieve details lazily. Public catalog caching is keyed by exact release/build/scope and contains no personal inputs. A private result, if cached at all, is owner-bound and keyed by profile/item/scenario/preferences/rule/evidence/authority revisions; revocation and corrections invalidate it. Personal payloads stay out of shared caches, URLs and ordinary logs. Persist only under existing saving/retention permissions; an audit trace does not authorize a new sensitive history store.

PostgreSQL supports persisted, indexable materialized results, with explicit refresh/freshness tradeoffs. That makes precomputed serving data a reasonable option, but a materialized view is not an acceptance/release mechanism. [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/rules-materializedviews.html). Keep the existing small Python/FastAPI service approach for an eventual local slice; measure concurrency and memory before adding worker processes. [FastAPI deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/).

Proposed measurement targets, not achieved results: warm first catalog page p95 under 300 ms; synchronous comparison of up to three units and twenty care items p95 under 1 second excluding external verification. Benchmark cold/warm reads, multiple sessions, payload size, pool waits, evidence-detail lookups and stale-response rejection on realistic data. Larger/external tasks return genuine pending status with a bounded job design before implementation. No LLM call belongs on the factual catalog critical path.

The existing consumer route remains held. Before real use: implement original-authority replay/release selection, exact serving joins and semantic reconciliation, privacy/owner isolation, capability-specific accepted policy/methods, meaningful adversarial evaluations and independent exact-scope acceptance. Technical static checks of this packet prove none of those capabilities.
